# cjtui 项目整体提案

## 1. 文档定位与当前状态

本文回答“为什么建设、面向谁、交付什么、范围如何控制、凭什么判断成功”。完整行为要求见 [需求说明](../requirements.md)，技术组织见 [总体架构设计](../architecture.md)，具体执行见 [工程任务](../tasks.md)。任务清单不能代替提案、需求或设计。

产品与仓颉包名均为 `cjtui`；GitHub 仓库仍为 `vchs6/terminal.ui`。当前仅完成开发仓库、工具配置及规划，产品实现状态为 planned、验证为 pending。本次补全文档不授权编写框架、原型、示例或基准源码，不发布制品；仓库文档与配置直接提交 main。

## 2. 背景与问题

终端应用通常同时处理业务状态、输入事件、文本宽度、布局、终端控制和屏幕刷新。当应用开发者直接组合这些底层机制时，容易把业务代码绑定到屏幕坐标和设备输出：文本缩短会残留、中文裁剪会破坏字符、弹窗关闭会恢复旧画面，组件也难以跨界面复用。

cjtui 作为一个全新的待开发项目，围绕应用作者如何构造界面来定义产品，再以统一的数据、生命周期和输出契约组织实现。项目提案、需求说明和架构设计分别明确产品目标、外部行为和技术组织，可以独立阅读并互相追踪。

## 3. 产品定位与使用者

cjtui 是使用仓颉实现、以字符网格终端为输出边界的声明式应用界面框架。它采用约定范围的 ArkUI 构造语法，将组件块、属性链、仓颉可观察状态、事件回调和自定义组件组织成统一开发方式。

| 使用者 | 典型工作 | 框架应承担的责任 |
|---|---|---|
| 终端应用开发者 | 定义页面、绑定业务对象、处理菜单和弹窗 | 自动布局、更新、合成、焦点与终端输出 |
| 组件作者 | 封装进度面板、信息列表等可复用界面 | 提供公开组合接口，不要求修改内核 |
| 应用维护者 | 排查字符、状态、终端兼容问题 | 明确诊断、能力矩阵、可复核快照和生命周期边界 |
| 框架维护者 | 扩展组件与适配后端 | 单一职责、明确契约、完整追踪及受控依赖 |

框架不要求应用采用编辑器、文档—视图或桌面 MDI 模型；业务对象的存在与生命周期由应用决定。

## 4. 建设目标与成功标准

| 目标 | 可观察成功标准 | 对应需求 |
|---|---|---|
| G1 构造方便 | U1–U5 通过同一套公开构造方法完成，普通应用无需手算全屏坐标、发送 ANSI 或手动刷新 | REQ-001 |
| G2 动态一致 | 同一业务状态可以驱动多个视图；挂载、更新、卸载与后台调度有确定行为 | REQ-002 |
| G3 界面可组合 | 布局、主题、圆角、阴影、菜单和嵌套覆盖层可组合，组件无需场景专用内核分支 | REQ-001、003 |
| G4 输出正确 | 字符簇不被拆坏，差分与写失败恢复正确，独立快照可用 | REQ-004、005 |
| G5 可交付维护 | 主库、示例、基准、产品文档和许可信息完整，开发资料不混入制品 | REQ-006、007 |

便利性不能只按代码行数判断。评审同时观察入口样板、重复配置、私有接口依赖、显式坐标、手动刷新和自定义组件封装成本；不编造极限行数或性能门槛。

## 5. 首版使用场景

| 场景 | 用户意图与操作 | 应见结果 |
|---|---|---|
| U1 最小应用 | 创建一个带样式文本的应用，从统一入口启动 | 使用合理默认主题，布局和刷新由框架完成 |
| U2 常规应用 | 组合水平菜单、主体容器、状态条和主题 | 键盘可导航；空间不足按公开规则处理 |
| U3 动态应用 | 仓颉后台任务提交进度、文本和颜色变化 | 内容变长/缩短及仅颜色变化均自动呈现，无残留 |
| U4 组合应用 | 将同一面板用于容器和带圆角阴影的模态弹窗，再打开弹出菜单 | 组件可复用；多层输入隔离、关闭和焦点恢复正确 |
| U5 泛化应用 | 使用现有公共接口组织不同业务界面 | 不新增内核业务特判，不绕过框架直写终端 |

语法和场景契约见 [用户构造设计](../ui-construction.md)。其中任何未编译示意都不得作为可运行示例交付。

## 6. 首版交付范围

产品必须交付声明式构造、自定义组件、文本/富文本、主题样式、横纵与弹性布局、状态和事件绑定、键盘焦点、容器、菜单、状态条、弹窗、多层合成、字符装饰、差分更新及完整文件快照。具体条件和异常行为由需求说明约束。

依赖使用中心仓 ansies 与 unicode，避免重建相同 ANSI 或 Unicode 内核。外部库不代替框架的安全、生命周期、区域裁剪和能力降级策略；可用边界由证据确认。

| 范围外事项 | 原因及边界 |
|---|---|
| 完整 ArkTS/ArkUI SDK、JS/TS 运行时和平台服务 | 采用语法子集，不承诺原平台运行环境 |
| CSS 选择器、外部样式及级联引擎 | 采用终端样式与属性链 |
| 字体家族/字号控制、像素画布、图像/视频、任意矢量变换 | 字符终端不能提供相同显示语义 |
| PTY、Shell 执行和完整虚拟终端 | 不属于当前界面框架必需范围 |
| 桌面式拖动、最大化、窗口平铺、强制文档模型 | 多层组合不等于桌面窗口系统 |
| 大量预制业务组件 | 先证明公共接口可组合和复用，再按真实需求扩展 |

未明确列为不支持的能力也不能自动视为已承诺。新增范围按治理流程决策。

## 7. 关键约束与参考技术方向

已确认约束：仓颉实现；包名 cjtui；组件块与属性链不是两套互斥 API；状态和回调使用仓颉；ansi/Unicode 使用指定中心仓依赖；输出以字符终端为边界；不开始产品实施；直接提交仓库。

参考方案采用“构造前端 → 节点与绑定 → 布局/绘制 → 覆盖合成 → 完整目标帧 → 差分 → 后端”的单一路径。模型和事件状态由 UI 执行域管理，应用通过公开绑定与调度入口接入。完整说明、替代方案与代价见架构设计。

当前固定 ansies 1.3.113、unicode 0.1.0，以 SDK 1.2.0 为验证版本；版本声明与工具可启动不等于产品依赖集成已通过。事实来源见 [依赖证据](dependencies.md)。

| 阶段 | 独立结果 | 放行条件 |

## 10. 风险与处置

| 风险 | 对产品的影响 | 处置与责任 |
|---|---|---|
| 所需 ArkUI 语法无法直接编译 | 公开构造方法不能按目标交付 | TASK-002 实测；不静默退化为对象配置，必要目标取舍交用户 |
| 外部库覆盖不足或版本行为差异 | 宽度/字符簇/解析与设计不符 | TASK-003 确认能力与最小适配，不建立平行内核兜底 |
| 平台输入和终端模式差异 | 键盘、缩放和恢复不可移植 | TASK-001 调查，TASK-004 冻结支持矩阵；不把 Linux CI 当全平台承诺 |
| 局部通过、整体难用 | 组件齐全但应用仍手工协调底层 | U1–U5 与构造便利性 Battle 作为整体门槛 |
| 产品和开发资料混杂 | 用户需要整个开发仓库才能使用 | TASK-023 检查真实 cjp 与干净解包；README 在线入口不制造包内断链 |
| 任务先于契约过度展开 | 实现返工或偏离要求 | 近期调查明确，远期任务保留候选，冻结契约后再细化 |

## 11. 完成定义与当前不确定性

完成必须同时证明用户构造目标、行为正确性、跨组件集成、生命周期与失败恢复、示例/基准可用及制品完整性。任务勾选、目录存在、环境 CI 绿色或设计认可均不能单独证明产品完成。唯一验收事实记录在 [验收矩阵](../acceptance.md)。

尚未完成的三类关键工作是语法路线实测、依赖行为实测及产品平台/终端矩阵。其问题、调查归属和决策影响已在需求与架构中明确；不以模糊“以后完善”替代，也不在本轮运行调查原型。
