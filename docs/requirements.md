# cjtui 需求说明书

## 1. 范围、状态与文档关系

本文件完整描述产品必须提供的外部行为、约束及可观察验收条件，不只是目录索引。面向一个全新的待开发项目，明确产品目标、能力范围、平台与运行约束。开发治理见 [AGENTS.md](../AGENTS.md)。产品与仓颉包名为 cjtui，仓库名保持 terminal.ui。

本文描述完整产品目标；Linux首片已有有限实现，已进入独立切片验收，已覆盖行为见docs/product/README.md及AC-048–053，不能视为完整REQ已通过。未覆盖的核心要求保持required / planned / pending；REQ-010 可选宿主扩展为extension，不能视为字符终端必需能力。required 表示目标范围，planned 表示未实现，pending 表示对应完整范围尚未验收通过；三者不互相替代。本文是需求全貌的阅读入口，OpenSpec 文件是对应场景投影，不独立增加另一套需求；变更时同步核对。执行治理仍由 AGENTS、Battle 与任务分解规范定义。

[整体提案](development/proposal.md)说明价值和范围，[架构设计](architecture.md)说明如何组织，[用户构造设计](ui-construction.md)细化开发者使用契约，[工程任务](tasks.md)负责执行状态，[验收矩阵](acceptance.md)负责证据。本文不记录另一套完成进度。

## 2. 使用者与系统边界

应用开发者提供组件声明、业务对象、可观察状态、仓颉回调和应用配置。框架负责组件生命周期、布局、输入分派、焦点、多层合成、刷新与设备状态恢复。终端和操作系统提供输入字节/事件、显示尺寸、设备输出及平台能力；实际字体字形不受框架控制。

业务数据不归框架所有，业务对象不强制绑定窗口生命周期。框架可以提供受控组件引用，但不得把直接设备操作作为普通界面开发入口。

## 3. 需求编号与场景

REQ-001–007 保留已有主编号，REQ-008–010为主题、输入和可选会话要求，REQ-011为跨平台及HarmonyOS必需目标；下列点号编号细化要求，不改变 TASK 与 AC 的稳定编号。每条细化要求的归属和验收入口在本文件末尾集中映射。

| 场景 | 用户输入/动作 | 必需结果 |
|---|---|---|
| U1 | 声明一个带样式文本并启动 | 合理默认主题与统一入口，不手动刷新 |
| U2 | 菜单、主体、状态条、主题组合 | 布局和导航一致，窄屏可预测 |
| U3 | 后台工作更新状态、文本和颜色 | 经调度自动刷新；缩短和仅颜色变化不遗漏 |
| U4 | 自定义面板复用于容器和多层模态界面 | 复用公开接口，裁剪、输入隔离、关闭及恢复正确 |
| U5 | 组合不同业务界面 | 不新增内核业务分支，不访问私有接口绕过契约 |

## 4. REQ-001：声明式构造与公共组件

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-001.1 | 支持约定的 ArkUI 组件块嵌套与属性链；业务表达式和类型使用仓颉 | 原始声明源码经正式入口编译；不能用手工转换或普通函数配置冒充 |
| REQ-001.2 | 支持可观察状态声明/绑定、条件/列表、自定义组件及仓颉事件回调 | 每类语法有最小可复现构建例及明确错误定位 |
| REQ-001.3 | 普通应用只用公开入口完成 U1–U5，不手算全屏坐标、发 ANSI、操作缓冲或 flush | 运行场景并检查用户侧代码，不依靠演示特判 |
| REQ-001.4 | 公开接口覆盖文本/富文本、换行/截断/对齐、样式、填充、布局、条件/列表、内容切换与组件组合 | 构造任务不需要私有 API，同类参数与默认值一致 |
| REQ-001.5 | 用户可封装组件并在普通容器和弹窗复用；预制组件也使用公开构造能力 | 同一面板原样放入不同宿主，不修改内核 |
| REQ-001.6 | 样式优先级为显式属性 > 可复用样式 > 主题 > 默认值；定义继承、未设置和复位 | 冲突配置给出确定样式；布局/边框/内边距不自动继承 |
| REQ-001.8 | 首版包含单行/多行文本与输入框、标签、水平/弹出菜单、按钮、单选框、复选框、进度条、状态栏、模态弹窗及分区容器 | 使用同一公开入口构造并操作各基础组件，不依赖演示特判 |
| REQ-001.9 | 视图可用受控 API 创建、按位置插入、移动及移除子组件，与声明式元素在同一序列融合 | A/B/C 中插入 X 得到指定顺序，统一布局、焦点和卸载；框架不排序数据 |
| REQ-001.10 | UI 与业务回调主要在编码期编写并编译；运行时动态组合执行已编译视图代码 | 无必须的运行时源码解释器；语言探针不冒充完整框架 |
| REQ-001.7 | 颜色/装饰遵循终端语义；不支持属性或语法给诊断，合法受限效果按公开策略降级 | 未知属性不能静默忽略；圆角可字符回退，不能声称控制像素曲率或字体 |

组件块和属性链属于同一构造方法。可有高级自定义绘制，但不允许把低层操作变成普通开发必经步骤；可选纯链式入口也不能取代组件块。

## 5. REQ-002：状态、身份、事件与生命周期

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-002.1 | 区分业务对象、可重新计算的组件描述和已挂载运行节点 | 描述重算不等于重新创建业务对象，也不错误丢失节点局部状态 |
| REQ-002.2 | 动态绑定保留计算规则及依赖，而不是只保存初值 | 同一状态绑定多个视图后均更新；普通不可观察变量不承诺自动更新 |
| REQ-002.3 | 节点身份按父关系、声明位置和显式 key 管理；列表使用稳定 key | 重排保留正确局部状态，不普遍用下标或对象地址代替 key |
| REQ-002.4 | 卸载释放订阅/事件资源，受控引用失效；业务对象可继续存在 | 卸载后无旧节点更新和失效引用访问；不销毁应用拥有的数据 |
| REQ-002.5 | 后台状态更新通过明确 UI 调度入口，禁止未同步修改节点树/缓冲 | 背景任务不直接操作节点或终端；事件顺序和可见结果可复核 |
| REQ-002.7 | 支持与响应式并存的显式通知，能定向到数据绑定、组件内容、状态、布局或结构 | 大批数据处理后一次通知更新相关视图；业务无需 flush，后台提交经 UI 调度 |
| REQ-002.8 | 业务拥有数据及排序/保留策略，视图决定组件呈现/显隐，框架管理运行节点 | 绑定重算不删除应用数据、不按数据变化猜测手动元素是否保留 |
| REQ-002.9 | 焦点、选中、展开等局部交互状态默认由组件管理，也允许公开绑定控制 | 受控和默认模式各有单一状态权威，不形成相互覆盖循环 |
| REQ-002.6 | 内容、样式、布局、显隐变化自动标记失效，合并一批更新；影响尺寸时重新布局 | 文本缩短清残留，仅改颜色也刷新，不要求用户追加重绘调用 |

首版依赖跟踪方式及宏生成边界须在语法验证后冻结。需求承诺的是可观察行为，不预先宣称某种机制已经可行。

## 6. REQ-003：布局、装饰、输入与多层界面

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-003.1 | 支持横纵分区、嵌套、弹性和内容切换；定义取整、余量、最小尺寸及空间不足处理 | 非整除和窄屏布局有确定结果，不要求用户手算全屏坐标 |
| REQ-003.2 | 分开布局区域、绘制区域和交互区域；区分边框、内边距和内容区 | 装饰不无意改变布局或命中，局部坐标经过统一转换 |
| REQ-003.3 | 圆角采用字符语义，阴影默认仅扩展绘制；服从祖先裁剪 | 阴影可越过本组件布局边界，但不越过有效裁剪，不扩大默认命中 |
| REQ-003.4 | 组件树负责逻辑生命周期，覆盖层栈负责显示顺序、锚点与输入 | 弹窗可按宿主契约溢出触发组件内容区，不临时关闭全部裁剪 |
| REQ-003.5 | 支持主界面、弹窗、弹出菜单和进一步模态确认；关闭父层同步关闭附属层 | 不留孤立层；模态输入不落到下层；纯装饰层不自动抢焦点 |
| REQ-003.6 | 菜单支持键盘导航、禁用项、选择与取消；状态条参与布局 | U2/U4 可操作，窄屏行为符合公开规则 |
| REQ-003.7 | 层关闭后恢复有效焦点；原触发节点失效时使用明确回退规则 | 不访问已卸载/禁用节点；非交互层不错误进入焦点序列 |
| REQ-003.9 | 支持横纵嵌套及固定行列、内容自适应、剩余空间比例分配，根布局充分使用视口 | 分配余量规则确定；不额外添加未声明留白，不强制拉伸内容字符 |
| REQ-003.10 | 读取实际尺寸并响应尺寸变化；小于应用最小尺寸仍按实际大小布局 | 固定 80×24 设备及缩小到更小尺寸均运行；不显示强制放大拦截、不强撑最小画布、不自行隐藏组件 |
| REQ-003.11 | 内容访问默认纵向滚动，表格允许横向滚动；单行编辑内部水平视口保持光标可见 | 滚动受组件视口裁剪，状态保留，分区显隐仅由应用显式决定 |
| REQ-003.8 | 底层状态可继续更新；移动、缩小、关闭使旧/新主体及阴影范围失效 | 关闭显示最新底层状态，不回写打开弹窗时的旧截图 |

当前不要求鼠标、拖动、最小化/最大化或桌面窗口平铺；是否扩展需单独立项。焦点、层和键盘导航是当前必需契约，不能以未实现鼠标为由省略。

## 7. REQ-004：字符网格、合成、刷新与恢复

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-004.1 | 内部坐标从 0 开始，尺寸使用行与显示列；负坐标、零尺寸及越界有确定规则 | 边界处理不会溢出缓冲或生成非法 ANSI 坐标 |
| REQ-004.2 | 单元结构化保存字符簇、样式及宽字符延续关系；有样式的空白与透明单元不同 | 合成、复制、擦除和裁剪不混淆透明和带背景空格 |
| REQ-004.3 | Unicode 策略统一到版本、字符簇、emoji、组合符和模糊宽度 | 不以字节/码点数当显示宽度；相同输入、尺寸和策略得到相同目标帧 |
| REQ-004.4 | 覆盖、裁剪、复制、清空和缩放不留下半个宽字符或孤立延续单元 | 右边缘中文/emoji、孤立组合符等用例保持规定不变量 |
| REQ-004.5 | 首版完整生成合成目标帧后做差分；不可见变化不输出屏幕更新 | 差分以完整画面为依据；M1不要求局部绘制，M2局部布局/绘制按REQ-004.8另行验收 |
| REQ-004.6 | 完整输出成功后才提交已显示基线；部分写失败使同步失效。完整重绘前须按受支持终端契约安全恢复解析/模式状态，无法确认则停止输出并报错 | 故障注入覆盖被截断的序列；不把未输出帧视为已显示，不在无法安全同步时宣称恢复 |
| REQ-004.8 | M2 必须按失效关系局部布局/绘制，与 M1 完整帧基线结果一致，公开 API 不变 | 颜色变化不重排无关节点，尺寸变化包含连带区域；移动/遮挡/宽字符用例对照完整帧，基准记录成本 |
| REQ-004.7 | 缩放使旧基线失效，统一管理光标及终端模式；正常、异常和取消退出均执行恢复 | 恢复动作可复核，失败明确报告；不宣称坏设备必然恢复成功 |

Unicode 的具体算法按中心仓 unicode / unicodewidth 的选型证据提供，框架负责适配与不变量。缓冲正确不等于不同终端字体的像素呈现完全相同，能力矩阵必须说明限制。

## 8. REQ-005：ANSI 输入、能力适配与文件导出

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-005.1 | ANSI 编码及适用解析基于中心仓 ansies；解析与编码分别维护支持矩阵 | SGR、基础/256/真彩色、光标和擦除范围有依据；不冒充完整终端模拟器 |
| REQ-005.2 | 增量输入跨块保留有界状态；畸形、未知、超长及末尾不完整序列有确定处理 | 分块与非分块处理一致；上限及超限结果在契约中可检查 |
| REQ-005.3 | 组件文本控制不能逃逸分配区或覆盖层，设备控制不得未经授权透传 | 恶意或未知控制输入不改变框架之外的设备状态 |
| REQ-005.4 | 结构化富文本与ANSI适配共享样式语义；程序员声明丰富颜色/属性，框架默认自动依据终端能力映射或降级，不要求应用判断支持级别；原始样式保留，手动覆盖仅可选 | 同一应用无override在不同真实宿主自动适配，未知能力保守且可诊断 |
| REQ-005.5 | 提供 ANSI 彩色与无 ESC 纯文本完整快照，默认含可见层和装饰 | 文件可独立消费，不依赖历史差分；纯文本无 ESC |
| REQ-005.6 | 规定快照编码、空白/背景、换行、初始与结束样式，报告写入失败 | 不能把未完成文件视为成功；产品说明给出彩色文件的查看条件 |

终端回复解析不自动满足富文本解析要求。依赖缺口按 TASK-003 调查及最小适配决策处理，不能另建无限制平行解析内核。

## 9. REQ-006：产品、文档与发布

主库 `cjtui`、最小/组合示例、独立渲染基准、产品说明、许可证及必要归属信息必须完整交付。示例与基准只依赖制品内主库和已声明外部依赖，不引用包外开发路径；最终验收在干净目录构建主库并运行示例/基准。

| 编号 | 必须满足的行为 | 可观察验收 |
|---|---|---|
| REQ-006.1 | 使用 package.include/exclude 只发布产品内容 | 实际 cjp 包含必要项目，不含开发规范、OpenSpec、技能、CI、历史源码、凭据及缓存 |
| REQ-006.2 | 开发者资料与产品资料职责分离，产品文档只陈述实际已验证能力 | 产品没有开发工具依赖；未实现语法稿不当可运行示例 |
| REQ-006.3 | 核对版本占用、依赖/传递许可证及包内依赖路径 | 不覆盖已有中心仓版本，不遗漏许可；配置字符串不替代真实打包结果 |
| REQ-006.5 | 产品版本使用三段非负整数主版本.次版本.修订号，当前开发版本0.0.0 | 清单与产品说明一致；不批量改写依赖/工具版本，不以版本字段当发布证据 |
| REQ-006.4 | 先完成最终交付验收，再进入获授权的发布动作 | 普通 slice CI 绿色不能作为产品可发布结论；当前不执行 publish |

## 10. REQ-007：工程治理、工具与证据

开发全程遵循 OpenSpec 与适用 Superpowers，必需技能要安装、验证并使用。项目任务位于 docs/tasks.md，具体变更按稳定编号转移状态权威，不能维护重复进度。L1/L2 不能直接编码；L3 有独立交付、验收和证据；L4 必须可检查，准入及质量规则引用 [工程任务分解规范](../ENGINEERING_TASK_DECOMPOSITION.md)。

CI 必须区分仓库/工具检查、已实现切片检查和完整发行检查；不能以跳过、空源码或降级必需失败制造完成结论。验证范围及结果复用统一按 AGENTS 第 11 节，不能每次编辑固定跑全量测试。决策权限、反熵治理、旧路径退役及直接提交方式按 AGENTS 第 10 节，不在本文复制另一套规则。

## 11. 非功能约束

| 编号 | 约束 | 评价与边界 |
|---|---|---|
| NFR-01 | 可学习与可组合 | U1–U5 代码审查与组合 Battle，不以组件数量代替可用性 |
| NFR-02 | 正确与确定性 | 固定输入/策略的帧断言、边缘字符、层关闭和故障注入 |
| NFR-03 | 资源有界 | 流解析缓存、帧尺寸与订阅生命周期必须有界；具体上限冻结时记录，不写无依据数值 |

| NFR-05 | 性能可测 | 基准记录尺寸、内容、更新负载、版本、环境与方法；没有事先证据不设虚构 FPS/延迟门槛 |
| NFR-06 | 可维护与可诊断 | 唯一职责与依赖边界、明确错误来源、可追踪任务及有效证据复用 |
| NFR-07 | 跨平台 | Linux、Windows、macOS、HarmonyOS为必需支持目标；SDK1.2.0/Linux x64仅为已有探针环境。具体OS/SDK/CPU/终端宿主矩阵经TASK-001/004冻结，各目标完整验收前不声称已支持；先完成 ANSI Linux 全部能力与验收，之后考虑其他平台 |
| NFR-08 | 非必需依赖隔离 | 不要求产品用户安装开发工具或 JS/TS 运行时，不重复实现指定外部库能力 |

HarmonyOS指用户要求的鸿蒙OS目标；具体系统/SDK版本、设备及合法交互式字符终端宿主必须调查并冻结，不默认为ArkUI图形应用、系统shell权限或POSIX终端接口均可用。OpenHarmony单独调查，结果不得直接替代商业HarmonyOS。跨平台指同源公开API和适配，不承诺同一可执行文件通用，也不引入像素/GUI后端、PTY或Shell执行。

需求跟踪：TASK-001/003调查、TASK-004冻结；TASK-038（Windows）、039（macOS）、040（HarmonyOS）、041（Linux）分别交付平台适配；TASK-020集成会话，TASK-023/024负责跨目标制品和整体验收。AC-001/003/004及AC-038–041/023/024为产品证据入口；本轮文档/独立审核AC-042/043不能代替这些产品结果。

### 18.1 实施顺序（用户后续裁决）

当前先完成支持 ANSI 转义序列的 Linux 终端全部约定能力和验收，再考虑 Windows、macOS、HarmonyOS；后者保留为后续必需目标，不作为 Linux 阶段前置条件。Linux 阶段通过不等于完整跨平台支持。 TASK-001/003/004 的当前输入、调查和冻结限定为 Linux；TASK-020 当前集成 Linux，TASK-023/024 当前验收 Linux 全功能、M1/M2、主题、编辑、动态构造、示例、基准和制品。后续平台仍须按 REQ-011 逐目标补齐相同核心验收，未运行的平台持续 pending。该顺序不减少任何 Linux 功能要求，也不把可选宿主扩展变成核心启动条件。
